# RCA — vendor-portal-458 redeploy FAILED (CrashLoopBackOff on boot) + login root cause confirmed

## Outcome of this redeploy
- Run `91dac54f-ac11-4864-a4f4-7fdb1aa7f591` (the new build with `backend/lib/bootstrap.py`) **FAILED at the `deploy_k8s` step** with `CrashLoopBackOff (early), restarts=3, lastExit=1/Error`. It was never promoted.
- Production is still serving the previous healthy run `02fa935a-...`. The site loads; **login is still broken exactly as before** (not newly down). The new build did NOT go live.

## Confirmed root cause (same underlying issue, now proven twice)
The production MongoDB credential in `MONGO_URL` is **NOT authorized on the `arun_vendor_auth` database**. Every operation the app issues against that second database returns:
```
pymongo.errors.OperationFailure: not authorized on arun_vendor_auth to execute command {...} code: 13, codeName: 'Unauthorized'  $db: "arun_vendor_auth"
```
The managed production Mongo user is scoped to the app's single provisioned database `vendor-portal-458-app` only. It has no rights on any other database, including `arun_vendor_auth` (AUTH_DB_NAME).

This is why:
- **Old run (02fa935a):** `POST /api/auth/login` → `_resolve_user` → `auth_db.users.find_one(...)` on `arun_vendor_auth` → code 13 → **500** on every login (superadmin and vendors). (The frontend shows the generic "invalid credentials" toast, which looked like a 401.)
- **New run (91dac54f):** the new `ensure_logins()` is `await`ed in `server.py` lifespan and its very first call `auth_db.users.count_documents({})` (bootstrap.py:69) hits the same code 13. Because it runs during FastAPI startup and the exception is unhandled, startup aborts: `ERROR: Application startup failed. Exiting.` → `Backend died, shutting down nginx` → CrashLoopBackOff. So the new build is strictly worse — the whole pod won't boot, not just the login route.

## Why the "populate the prod auth DB" approach cannot work as designed
`ensure_logins()` / `migrate_auth_db.py` both READ and WRITE the `arun_vendor_auth` database. The prod credential cannot read or write that database at all (code 13 on find, count, aggregate, createIndexes). No amount of seeding/migrating into `arun_vendor_auth` will work, because the running app cannot access that DB in production. It worked in preview only because the preview Mongo user is not scoped to a single DB.

Important data fact: the 19 logins (owner `arunenterprises2023@gmail.com` / id `u-admin-arun`, plus the AE00xx vendors) ALREADY exist in the authorized database `vendor-portal-458-app`, in its `users` collection (with password hashes). The owner's `role` there is `admin` (not `superadmin`).

## Recommended fixes (pick one; both avoid the unauthorized DB)

### Option A — fastest, no code change (USER, Secrets tab)
In Deployment Panel → Secrets, set **`AUTH_DB_NAME` = `vendor-portal-458-app`** (identical to `DB_NAME`), then redeploy.
- Effect: `auth_db` becomes the primary, authorized database. All auth reads/writes, index creation, and the new `ensure_logins()` count/copy then run on the DB the credential owns. The 19 logins are already there, so login starts working and the new build boots cleanly.
- Note: owner `u-admin-arun` currently has `role: admin`. If any SuperAdmin-only feature checks the role, that one document still needs `role: superadmin` (E1 can set this, or `ensure_logins` owner-promotion path will handle it once it can write).

### Option B — permanent code fix (CODE, E1)
Change `backend/lib/db.py` so auth collections live in the PRIMARY app database instead of `client[AUTH_DB_NAME]` — e.g. default `AUTH_DB_NAME` to `DB_NAME`, or make `auth_db = db`. The two-database design is fundamentally incompatible with managed production Mongo (single-DB credential).
Additionally (resilience): in `server.py` lifespan, do not let `ensure_logins()` hard-crash the whole backend — wrap it so a bootstrap failure logs an error but still allows the app to start. As written, awaiting it unguarded turned a login-only fault into a total boot outage.

Do NOT attempt to grant the Mongo user access to a second database — the cluster/credentials are platform-managed and this is not user-configurable.
